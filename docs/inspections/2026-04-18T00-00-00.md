#### H3 — duplicate_semantics: `browserDownloader` is copied verbatim across two packages
**Files:**  
- `internal/app/browse.go:21–171`  
- `internal/unified/browse.go:21–171` (comment: "Implementation copied from internal/app/browse.go for feature parity")

**Check:** duplicate_semantics  
**Confidence:** High [Grep fallback]

Both files define identical `browserDownloader` struct, `Download`, `DownloadWithProgress`, `Uncache`, `Sync`, `HasBeenModified` methods, and `progressReader` struct with its `Read` method. The `unified` copy even acknowledges it is copied. Any bug fix or enhancement to one copy must be manually mirrored to the other.

The `Download` method differs in one subtle way: in `app/browse.go:28` it returns `err == nil, err` correctly forwarding errors; in `unified/browse.go:28` it returns `d.DownloadWithProgress(...) == nil, nil` — the second return value is always `nil`, so a download error causes `Download` to return `(false, nil)` instead of `(false, err)`, silently swallowing the error.

**Impact:** Logic divergence is already present. Bug fixes to one copy won't propagate. The `tui.Downloader` interface should be implemented once in a shared location.

#### H5 — silent_failure: `unified/browse.go` `Download` method silently drops errors
**File:** `internal/unified/browse.go:28–30`  
**Check:** silent_failure  
**Confidence:** High [Grep fallback]

```go
func (d *browserDownloader) Download(owner, repo, bookID, release, asset, sha256 string) (bool, error) {
    return d.DownloadWithProgress(owner, repo, bookID, release, asset, sha256, nil) == nil, nil
}
```

The second return value is hardcoded to `nil`. When `DownloadWithProgress` returns an error (network failure, asset not found, cache write error), the caller receives `(false, nil)` — no error is propagated. The equivalent in `internal/app/browse.go:28` is also flawed (`return err == nil, err` is still returning the error when `err != nil` so that one propagates correctly, but the unified copy never does).

**Impact:** The TUI browse view will silently fail to download books without reporting errors to the user.

#### M1 — scope_analysis: `cache.Manager.Path` ignores `owner` and `bookID` parameters
**File:** `internal/cache/paths.go:25`  
**Check:** scope_analysis  
**Confidence:** High [Grep fallback]

```go
func (m *Manager) Path(owner, repo, bookID, assetFilename string) string {
    return filepath.Join(m.baseDir, repo, assetFilename)
}
```

The `owner` and `bookID` parameters are accepted but silently discarded. The cache layout is `<baseDir>/<repo>/<assetFilename>`. This means two books with the same `repo` and `assetFilename` but different owners would collide, even though the function signature implies they are distinct.

Similarly `EnsureDir` at `paths.go:36` takes `owner` and `bookID` but ignores them too, creating only `<baseDir>/<repo>`.

**Impact:** In multi-owner scenarios (e.g., two shelves with different owners pointing to repos of the same name), files would silently overwrite each other. The `owner` should be part of the cache path to ensure isolation.

#### M2 — silent_failure: `os.WriteFile` uses mode `0644` for sensitive files
**Files:**  
- `internal/app/open.go:149` — poppler hint marker  
- `internal/cache/html_index.go:30` — HTML index file

**Check:** silent_failure / scope_analysis  
**Confidence:** High [Grep fallback]

`html_index.go` writes the library HTML index at `0644`, making it world-readable. This file can contain book titles, authors, file paths on disk, and shelf metadata. On a multi-user system, this leaks library metadata.

`open.go:149` writes a sentinel marker file at `0644` — this is not sensitive, but inconsistent with the rest of the codebase's `0600` policy for user-specific data.

Compare: `catalog.yml` writes use `0600` (via `os.WriteFile(catalogPath, data, 0600)`); cache book files are written through `os.Create` which defaults to `0666 & ~umask`.

#### M3 — context_propagation: All HTTP requests are created without `context.Context`
**Files:** `internal/github/client.go:78`, `internal/github/assets.go:52,89,115`, `internal/github/contents.go:32,70`, `internal/ingest/resolver.go:96`, `internal/migrate/scan.go:43`  
**Check:** context_propagation  
**Confidence:** High [Grep fallback]

No production HTTP request in the codebase uses `http.NewRequestWithContext`. Every call uses `http.NewRequest(method, url, body)`. There is no mechanism to cancel long-running downloads or uploads (e.g., when a user presses Ctrl+C mid-upload in the TUI), aside from cancellation channels that only work within bubbletea's goroutine model and do not cancel the underlying HTTP connection.

The `github/client.go` comment documents a 5-minute timeout on the HTTP client, which provides an outer bound but not cancellation on user request.

**Impact:** Large file uploads/downloads cannot be interrupted at the HTTP layer. Goroutine leaks are possible during TUI quit events, though in practice the process exits shortly after.
